# One path for book data (covers, description, bio, rating): plan (owner approved 2026-10-30)

## Owner decisions (recorded)
- Yes to stages S1-S4. The admin star also **publishes the cover to the catalog and refreshes this device's catalog at once** (admin/developer mode only; a normal reader's star stays a personal pick on their own devices).
- The old shared-covers list (Cloudflare KV, `functions/api/covers.js`, device key `readlife.sharedCovers1`) is **migrated into Supabase**, then KV is removed if that leaves cleaner code. The cover picker and the admin `<>` developer tool must keep working throughout.
- Rules: Supabase is the one shared source of truth for approved data. The device catalog copy is a cache kept in step with Supabase, never a second source. Every screen (cards, Book Info, picker, `<>`, Review Catalog) follows the same read / publish / refresh path. Personal reading data and personal cover picks stay separate from shared catalog rows.

## Why it is not one path today (verified in code by the previous session)
Separate sources, each screen asks its own: published catalog copy, shared-covers list (`/api/covers`, can disagree with the catalog), your own pick, what the shelf/search result carried, and live Apple/Google/Open Library lookups run separately by Book Info, the cover resolver and the cover picker.
1. Review Catalog reads the database directly and lists every stored version, including unpublished; Book Info only sees published values. A rating seen only in Review Catalog is probably stored but not published (check the selected/published flag first). A loose-matching bug can also hide a published rating (re-find it in the catalog cover/rating match code; the audit notes were lost to a quota stop).
2. The cover picker never reads the database: it asks the providers live every time ("Finding more covers..."), so it shows 1 cover while `<>` shows 4 stored versions.
3. Cards use one lookup chain and can give up on a book; the picker uses a wider live search. They disagree (placeholder on a card, cover in the picker).
4. A star is a device-only pick that applies at once to cards with the same title+author; it is not published, and other devices only get published covers through catalog sync (checks at most every 10 min unless forced). 5. Owner report 2026-10-30 (still open after C1): reopening the app after a few hours or a day shows cover placeholders, then the covers appear. A cover already seen should stay put. C1 keeps the saved lists and URLs, so the remaining suspects are the image bytes (iOS drops the cache while the app is closed; check `public/sw.js` and `functions/api/cover-img.js` caching) and covers being resolved only after first paint. ## Target order for every screen (one function per book)
1. your personal pick -> 2. published catalog (already on the device, instant) -> 3. what the shelf/search result already carries -> 4. live lookup, only for what is still missing. Placeholder only if none of these has anything.
